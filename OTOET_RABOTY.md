## 2. Линтер

Я понял линтер так (по восстановленному содержанию статьи и документации инструментов): это статический анализатор, который ищет в коде ошибки, потенциально опасные конструкции и нарушения стиля **без выполнения программы**. В отличие от компилятора/`tsc`, он ловит не только синтаксис и типы, но и «плохие практики» — неиспользуемые переменные, мутации пропсов, нарушение правил хуков React.

В моём проекте стоит **Oxlint** (`oxlint ^1.81.0`) — быстрый линтер на Rust. Я выбрал его вместо ESLint ради скорости: проверка 25 файлов заняла **47 мс**, тогда как ESLint на таких проектах считается на секунды.

Моя конфигурация `.oxlintrc.json`:

```json
{
  "plugins": ["react", "typescript", "oxc"],
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": ["warn", { "allowConstantExport": true }]
  }
}
```

Запуск: `npm run lint` → `oxlint`.

Я реально выполнил `npx oxlint` (05.11.2026) и получил **0 ошибок, 22 предупреждения** в 25 файлах (116 правил). Вот что нашлось и как я это трактую:

| Предупреждение | Кол-во | Мой комментарий |
|---|---|---|
| `react(purity)` — вызов impure-функций при рендере (`Date.now()` в обработчиках) | 5 | Считаю реальными кандидатными багами: `Tasks.tsx:130` и другие места нарушают чистоту рендера |
| `eslint(no-unused-vars)` — неиспользуемый параметр `catch (e/error)` | 6 | Косметика: перехожу на `catch {}` (optional catch binding) |
| `eslint(no-unused-expressions)` | 4 | Вероятно мой intentional short-circuit (`a && b()`) |
| `react(set-state-in-effect)` | 3 | Каскадные перерисовки, например `useSync` в `sync.ts:475` |
| `react(only-export-components)` | 1 | Fast Refresh ломается, если файл экспортирует не только компоненты (например `ui.tsx`/`icons.tsx`) |
| `react(refs)` — доступ к ref при рендере | 1 | `ref.current = state` во время render (`sync.ts:470`) |
| Прочие (`no-constant-condition`, unused param `modifier`) | 2 | Локальные мелкие правки |

Отдельно я заметил, что линтер косвенно помогает мне соблюдать часть SOLID: `react/rules-of-hooks` и `react/purity` держат компоненты предсказуемыми (**SRP**: компонент делает одно дело и не имеет побочных эффектов), а `only-export-components` фактически навязывает разбиение файлов по ответственностям (**SRP/ISP**): хуки, константы и компоненты — в разных модулях. Именно так у меня уже сделано: `lib/storage.ts` (данные), `lib/api.ts` (сеть), `components/*` (UI), `pages/*` (экраны).

При этом я осознаю ограничение: ни ESLint, ни Oxlint не проверяют архитектурные связи между модулями. Для контроля DIP/ISP нужна отдельная библиотека (dependency-cruiser, eslint-plugin-boundaries) — у меня её нет.

## 3. Форматер

Форматтер, как я его понимаю, автоматически приводит код к единому стилю (отступы, кавычки, переносы строк) и снимает эти споры с линтера. Стандарт индустрии для JS/TS — **Prettier**; альтернатива на том же движке, что и мой линтер, — **`oxfmt`** (Rome/Oxc).

Проверкой (`npm ls prettier` — пусто; `.prettierrc*`, `prettier.config.*`, `.editorconfig` отсутствуют) я установил: **форматтер в проекте не настроен**. При этом во всём моём коде последовательно используется один стиль: без точек с запятой, одинарные кавычки, висячие запятые (multi-line trailing comma), ширина ~80–100 символов. Стиль выдержан вручную/дисциплиной редактора, и я пришёл к выводу, что это хрупко для командной работы.

Я для себя определил минимальную настройку:

```json
// .prettierrc
{
  "semi": false,
  "singleQuote": true,
  "trailingComma": "all",
  "printWidth": 90
}
```

```jsonc
// package.json → scripts
"format": "prettier --write src",
"format:check": "prettier --check src"
```

Плюс связка с VS Code: `"editor.formatOnSave": true` + `"editor.defaultFormatter": "esbenp.prettier-vscode"` в `.vscode/settings.json`. После этого правила стиля можно убрать из линтера: Prettier отвечает за форматирование, Oxlint — за качество кода. Я осознал это как типичное разделение ответственности **между двумя инструментами** — тот же SRP, применённый к инфраструктуре.

## 4. Анализ кода проекта на соответствие SOLID

Основа — статья SprintCode: пять принципов Роберта Мартина адаптированы для JS/React; автор подчёркивает, что SOLID — руководящие принципы, а не жёсткие правила, и слепое следование им вредит маленьким проектам. Я разобрал свой код `my-react-pwa`.

### S — Single Responsibility Principle: соблюдается

Разделение по модулям у меня выполнено чисто:

- `storage.ts` — только реактивный стор поверх localStorage (`createStore` + подписки);
- `api.ts` — только внешние HTTP-запросы (курсы валют) и их кэш;
- `appearance.ts`, `notifications.ts`, `hooks.ts`, `sync.ts` — по одной теме каждый;
- Компоненты страниц (`Tasks.tsx`, `Notes.tsx`...) отвечают за UI своей сущности.

Единственная перегрузка, которую я нашёл: `hooks.ts` совмещает 3 разные темы (эффект темы, статус сети, форматирование дат) — формально три причины менять файл. Я понял, что стоит выделить `hooks/useThemeEffect.ts`, `lib/format.ts`.

### O — Open/Closed Principle: частично

Хорошо закрытая точка расширения — фабрика `createStore(key, initial)` в `storage.ts`: новый тип данных добавляется вызовом без изменения существующего кода. Плохая иллюстрация OCP — `sync.ts`: логика применения удалённого состояния (`applyRemote`) захардкожена на конкретный список сторов `notes/tasks/habits/settings`; при добавлении пятого стора придётся **модифицировать** тело функции вместо расширения. Я пришёл к мысли итерироваться по списку `{ store, key }`, тогда sync будет закрыт для правок.

### L — Liskov Substitution Principle: неприменимо напрямую

Классического глубокого наследования у меня нет (функциональный стиль + хуки). Роль «подстановки» играют однотипные сторы: все четыре созданы `createStore` и взаимозаменяемо используются в `useStore`/`startAutoSync` — контракт `get/set/subscribe` соблюдается всеми, то есть LSP выполняется по построению.

### I — Interface Segregation Principle: соблюдается

Интерфейсы (`SyncPayload`, `CurrencyResult`, типы из `types.ts`) узкие и клиенто-ориентированные: `useCurrency(from, to)` зависит только от `CurrencyResult`, а не от всего API-модуля; `useSync` возвращает компактный `{ status, connection, lastSyncAt, lastError, enabled }` вместо полного внутреннего состояния модуля.

### D — Dependency Inversion Principle: самая слабая точка

Высокоуровневый модуль `sync.ts` зависит от **конкретных реализаций напрямую** (import `notesStore, tasksStore, ...` из `./storage`, жёсткий вызов `fetch('/api/...')`, `EventSource`). Свойства этой зависимости смягчены моей осознанной архитектурой («localStorage — источник истины, сервер — зеркало»), но:

- `syncNow()/pushNow()` невозможно протестировать без реального сервера и localStorage — прямое следствие нарушения DIP (в разделе 5 видно, как это чинится абстракцией `Transport`);
- по статье (паттерн «Стратегия»/инъекция), мне нужно принимать «источник данных» и «транспорт» параметром/через контекст, а конкретные сторы подключать на composition-корне в `main.tsx`.

### Итог по SOLID

| Принцип | Моя оценка | Одна строка пояснения |
|---|---|---|
| S | ✅ | Чистое разбиение `lib/` ↔ `components/` ↔ `pages/`; мелкая склейка тем в `hooks.ts` |
| O | ⚠️ | `createStore` открыт для расширения; `applyRemote` требует правок при росте числа сущностей |
| L | ✅ | Однотипные сторы взаимозаменяемы через общий контракт |
| I | ✅ | Узкие интерфейсы хранилища и результатов запросов |
| D | ❌ | Глобальные импорты сторов и `fetch` внутри бизнес-логики `sync.ts` |

## 5. Тестирование React (по статье PurpleSchool)

### Пирамида тестирования, которую я усвоил из статьи

1. **Unit** — отдельная функция/компонент (Jest/Vitest + React Testing Library).
2. **Интеграционные** — связки компонентов (например форма + контекст темы).
3. **E2E** — реальные пользовательские сценарии в браузере (Cypress/Playwright).

Инструменты: Jest, RTL (тестирует поведение пользователя, а не внутренности компонента), Cypress, MSW (мок сетевых запросов). Подходы: Arrange-Act-Assert, один тест — одно поведение, доступные селекторы (`getByText`, роль), снапшоты осторожно; мокирование через `jest.fn()`/`jest.mock`, асинхронщина через `findByText`; хранение тестов рядом с файлами (`Component.test.tsx`); CI-прогон через GitHub Actions (`npm test -- --coverage`).

### Состояние в моём проекте

Я проверил: **тестов в проекте нет** (ни одного `*.test.*`/`*.spec.*`, тестовых зависимостей в `package.json` тоже). Практическую ценность их появления я вижу именно в местах, найденных линтером и анализом SOLID:

- `sync.ts` — самый сложный модуль (SSE, поллинг, разрешение конфликтов `updatedAt`, обработка 401). Сейчас он почти нетестируем из-за прямой зависимости от `fetch`/`EventSource` (DIP). Первая цель тестирования после введения абстракций — unit-тесты логики `syncNow` с мок-транспортом и MSW-подобными заглушками `/api/sync`.
- `storage.ts` — `createStore` идеален для unit-теста: get/set/update/subscribe/reload изолированно, без DOM.
- `Tasks.tsx`/`Habits.tsx` — интеграционные тесты поведения: клик отмечает задачу выполненной; здесь же ловятся нарушения purity, найденные `oxlint` (`Date.now()` при рендере даёт нестабильные assertion'ы).
- E2E (Playwright) — я решил разумно ограничить одним сценарием «офлайн → онлайн → синхронизация», т.к. офлайн-режим является ключевой функцией PWA.

### Стек, который я для себя выбрал (с учётом Vite)

Статья рекомендует Jest; для моего Vite-проекта естественнее **Vitest** (API совместим с Jest, нативная интеграция с `vite.config.ts`):

```bash
npm i -D vitest @testing-library/react @testing-library/jest-dom jsdom msw
```

```tsx
// пример unit-теста для области storage.ts
import { createStore } from './storage' // требует export — сейчас фабрика не экспортируется

test('set обновляет значение и уведомляет подписчиков', () => {
  const s = createStore('demo', 0)
  let notified = 0
  s.subscribe(() => notified++)
  s.set(5)
  expect(s.get()).toBe(5)
  expect(notified).toBe(1)
})
```

Отдельный практический вывод, к которому я пришёл: чтобы покрыть тестами ядро синхронизации, сначала нужно выполнить рекомендации раздела 4 (DIP) — тесты и архитектура связаны напрямую, что подтверждает тезис обеих статей: SOLID повышает тестируемость.

## 6. К чему я пришёл (выводы)

Подводя итог работе, я пришёл к таким результатам:

1. **Форматтер в проекте отсутствует** — я это установил проверкой и решил, что нужно добавить `.prettierrc` + расширение Prettier + `formatOnSave`, чтобы закрепить текущий стиль механически.
2. **Настроек IDE в проекте нет** — я нашёл отсутствие `.vscode/settings.json` и `.editorconfig` и понял, что их нужно создать для единых правил у всех участников.
3. **Линтер я прогнал реально**: 0 ошибок и 22 предупреждения oxlint; разбирать начну с 5 × `react(purity)` (реальные риски при будущих React Compiler-оптимизациях) и `refs-during-render` в `sync.ts`.
4. **SOLID-анализ показал мою слабую точку — DIP**: я пришёл к выводу, что нужно вынести `Transport`/источник данных из `sync.ts` за абстракцию и сделать `applyRemote` табличным (это же закроет OCP).
5. **Тестов у меня нет**, и по прочитанной статье я выбрал стек Vitest + RTL + MSW; начать планирую с unit-тестов `storage.ts`, затем интеграционные для `Tasks/Habits`, один Playwright-E2E на офлайн-сценарий.
6. **`hooks.ts` я признал перегруженным** по трём темам и решил разбить его по ответственностям (SRP).

Главное, что я вынес из работы: все пять тем связаны между собой. Линтер подсвечивает нарушения чистоты компонентов, SOLID-анализ объясняет, *почему* модуль нетестируем (DIP), а тестирование даёт мотивацию исправить архитектуру. Инструменты (IDE, DevTools, линтер, форматер) я рассматриваю теперь не как отдельные настройки, а как единую инфраструктуру качества кода.
